# fable-emu harness

Fable 5相当のモデルは、詳細な指示を与えるほど出力品質が下がる（規定的すぎる指示が単一パスの判断力を阻害する）特性を持つ。一方、それ以外のモデルにはその内部特性が無い。このharnessは、Fable 5が重みの内部で暗黙にやっている「分解・独立検証・長期一貫性の維持」を、モデルを問わず外部工程として明示的に強制することで代替する。

参考: https://zenn.dev/ait/articles/fable-emu-opus-harness

**移せるもの／移せないもの**（着手前に自覚しておくこと）

| 項目 | harnessで移せるか |
|---|---|
| 分解・独立検証・長期一貫性 | ✓ 外部工程として強制できる |
| 進捗の裏付け・セッション間学習 | ✓ 外部記憶＋検証ループで代替できる |
| 単一パスの正答率そのもの | ✗ 重み由来。プロンプトでは埋まらない |
| 分解不可の一発洞察 | ✗ 埋まらない。Fable 5系モデルを使う判断をする |

検証は能力を増幅するが、創出はしない。「使いにくい」「見た目が違和感ある」のような主観的評価や、完了条件を事前に1行で書けない創造的な問い自体は、この仕組みでは拾えない。無理に検証可能な形に押し込めようとしないこと。

## §C 設定値

このプロジェクトでのharness設定。調整はこの節だけを書き換えれば全体に反映される。

- `PLAN_DIR` = `plans/`（リポジトリ直下。レビュー資産としてコミットする。機密性の高い計画のみ `~/.claude/projects/<repo>/plans/` に逃がす）
- `MEMORY_DIR` = ネイティブのproject memory（このセッションの自動memory機構。`~/.claude/projects/<repo-slug>/memory/` 相当）をそのまま使う。`plans/` 配下には保存しない（split-brain防止）
- `MAX_FAIL` = 2（`/verify`が連続でこの回数FAILしたら、修正を続けず再計画〔`/plan`のやり直し〕に切り替える）
- `BESTOF_N` = 3（`/bestof`で生成する案の数）

## §P プロファイル

- 立場：ソフトウェアエンジニア（このリポジトリのオーナー）
- 判断を委ねる範囲：実装の詳細・ファイル構成・ライブラリ選定は委ねてよい。破壊的操作・公開判断・外部送信は必ず確認する（既存のグローバル方針と同じ）
- 成果物の既定種別：コード（TypeScript/Next.js中心）とドキュメント
- 検証の既定手段：`tsc --noEmit` / `eslint` / `next build`、既存の`.claude/backend-code-review-checklist.md`、実ブラウザでの動作確認

## §0 ゲート判定

非自明なタスクに着手する前に、次の4つを自問する。

1. 不可逆な操作を含むか（DB破壊的マイグレーション・force push・秘密情報の取り扱い等）
2. 複数の領域・ファイル群にまたがるか（route/service/repository一式、スキーマ＋フロント複数箇所、等）
3. 完了条件を今すぐ1行で書けないか
4. 同種の作業で過去に手戻り・レビュー指摘が発生したことがあるか

**1つでもYes** → 下記「§1 実行フロー」を完全に踏む。
**全てNo**（質問応答、typo修正、1行程度の自明な変更、既存パターンの単純な横展開等） → ゲート免除。直接実行してよい。

ゲートを課すかどうかで毎回悩まない。迷ったら軽い方（ゲート免除）に倒し、`/verify`だけ後から挟む形でも構わない。全タスクに全ゲートを課すと動作が遅くなるだけで品質は上がらない。

## §1 実行フロー（PLAN → EXECUTE → VERIFY → REPORT）

ゲート対象タスクは、この順序を飛ばさない。

1. **PLAN**：`/plan`スキルを使う。scoutによる並列偵察 → plannerによる`plans/`配下への計画ファイル作成 → ユーザーの承認を待つ。承認前にEXECUTEへ進まない
2. **EXECUTE**：計画のサブタスク（ST）単位で実装する。1つのSTを終えるごとに次のSTへ進む前に一息入れ、計画からの逸脱がないか確認する
3. **VERIFY**：`/verify`スキルを使う。verifierサブエージェントに独立した文脈で完了条件と突き合わせさせる
   - FAILなら修正して再度`/verify`
   - 連続`MAX_FAIL`回FAILしたら、同じ方向で粘らず`/plan`に戻って計画自体を見直す
4. **REPORT**：計画ファイルの進捗ログに結果を記録し、ユーザーに簡潔に報告する

長時間・多ステップのランでは、定期的に`/checkpoint`を挟んで計画からのドリフトを検知する。重い判断（設計方針の選定、複数実装案からの選択等）が必要な箇所では`/bestof`を使う。

## §2 証拠規律

- 「動くはず」「たぶん通る」で完了扱いにしない。`tsc`／`eslint`／テストコマンド／実際のcurlやブラウザ操作など、ツール出力で裏付けを取ってから完了と報告する
- verifierへの報告は、実装時の経緯や所感を混ぜず、完了条件と成果物への参照のみを渡す（後付け正当化バイアスを防ぐ）
- ツールで機械的に判定できない項目（UXの違和感、見た目の評価等）を、無理に機械判定できる体裁に整形しない。「目視確認が必要」と明示する

## §3 境界と続行規律

- 計画の「やらないこと」に書いた範囲を、実装中に気づいた別件のついで直しで越境しない。気づいた別件は計画ファイルの「要確認」またはメモリに記録し、別タスクとして扱う
- 前提が崩れた（想定と違うファイル構成だった、依存が無かった等）場合は、その場で無理に押し通さず一度止まってユーザーに確認する

## §4 報告規律

- 完了報告は「何をしたか」「どう確認したか（ツール出力の要約）」「次にやることがあれば何か」を簡潔に。過程の詳細な実況は不要
- FAILや手戻りが発生した場合は、隠さずそのまま報告する（体裁を整えるために検証結果を書き換えない）

## §5 委譲規律

- scout／verifier／judgeへの委譲は、独立した文脈での偵察・検証・比較が価値を持つ場面（§0でYesと判定した場面）に限る。単純なタスクにまで委譲すると、コストが増えるだけで品質は上がらない
- 委譲時は完了条件・参照すべきファイル・スコープを明示する。委譲先が自分で前提を推測しなければならない状態で投げない

## §6 過剰実装禁止

- 計画にないリファクタリング・抽象化・将来を見越した拡張を、検証や実装のついでに混ぜ込まない（`app/CLAUDE.md`の「絶対に守ること」と同じ方針）
- `/bestof`で複数案を比較する際も、シンプルな案を過剰実装というだけで不利に評価しない

## §7 メモリ規律

- 恒久的に価値のある知見（原因の特定に時間がかかった不具合、非自明な設計判断の理由等）は、ネイティブのproject memory（`MEMORY_DIR`）に記録する。`plans/`配下の進捗ログは作業メモであり恒久記録ではないため、両者を混同しない
- 記録すべきか迷う情報は、次にこのリポジトリを触る人（人間でもAIでも）が同じ調査を繰り返さずに済むかどうかで判断する

## §8 並行セッション規律

- 同じファイル・同じ計画に対して複数セッションが同時に書き込む状況を避ける。既に進行中の作業（未コミットの変更、他セッションが触っている形跡）を見つけたら、上書きせず先に状況を確認する
- 計画ファイル（`plans/`配下）は、並行して進める作業ごとに別ファイルに分ける
