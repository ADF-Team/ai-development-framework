# バックエンドコードレビュー チェックリスト

`app/src/app/api` 配下（route/service/repository）のコードを**書く時**・**レビューする時**の両方でこのチェックリストを使う。目的は「レビュー指摘→修正→再レビュー→新たな指摘」の往復を減らすこと。実装時点でここに挙げた項目を満たしていれば、レビューで指摘される数はその分減る。

対象: `app/src/app/api/**`, `app/src/lib/api/**`, `app/src/lib/services/**`, `app/src/schemas/**`（バックエンドで使うもの）, `app/prisma/schema.prisma`

---

## 1. 入力バリデーション（zod）

- [ ] スキーマの`.max()`は**必ずDBカラムの制約（`@db.VarChar(n)`等）と一致**させる。一部のフィールドだけ長さ制限を付けて他を漏らさない（`schema.prisma`の対応カラムを都度確認する）
- [ ] 同じフォーム／同じリソースの複数フィールド間で、`.trim()` `.min()` `.max()`のポリシーを揃える（あるフィールドだけtrimし忘れる、片方だけmaxLengthが違う、というズレを作らない）
- [ ] `PATCH`など部分更新のスキーマは、全フィールドを`.optional()`にするだけで済ませず、**最低1フィールドは必須**にする`.refine()`を付ける（空の`{}`が素通りしないか確認する）
- [ ] フロントエンドの`<Input maxLength={...}>`と、対応するzodスキーマの`.max()`は同じ定数（`constants/validation.ts`）を参照させる。数値を書き分けない

## 2. リクエスト処理・エラーハンドリング

- [ ] `request.json()`の呼び出しは**try/catchの中**で行う（外に置くと不正JSONで未処理の例外になる）。パース失敗時は422で`{ detail }`を返す
- [ ] 同じ定型処理（JSONパース、Prismaエラーマッピングのtry/catch等）が2箇所以上に出てきたら、共通ヘルパーに切り出す（`src/utils/`または`src/lib/services/`）
- [ ] Prismaのエラーコードは意味の違いを保つ：`P2025`（未検出）と`P2023`（型不整合・不正な形式の値）を同じステータス（例：両方404）にまとめない
- [ ] `P2002`（一意制約違反）は違反した列（`error.meta.target`）に応じたメッセージをマップで管理し、`if`分岐を列の数だけ増やさない設計にする
- [ ] `mapPrismaError`のような共通マッパーが対象外にするエラー種別（`PrismaClientValidationError`等）がAPIに直接届かないよう、**手前のzodバリデーションで防ぐ**（マッパー側でカバーしようとしない）
- [ ] `withPrismaErrorMapping`のようなエラーマッピングのラッパーは、更新系（create/update）だけでなく**読み取り系（findMany/findUnique等）にも同様に適用**する。「書き込みだけ」「更新だけ」ラップして一覧取得を漏らしていないか確認する
- [ ] 成功・エラーレスポンスは`route.ts`内で`NextResponse.json`を直接組み立てず、`src/lib/api/response.ts`の`apiSuccess`/`apiError`を使う（レスポンス形式を変更する際に1箇所で済むようにする）
- [ ] JSONパース＋zodバリデーション＋422応答は毎回書き下さず、共通ヘルパー（`src/utils/parseRequestBody.ts`）に集約する

## 3. 認証・認可

- [ ] 新しいAPIルートを追加する際、「TODO: 認証チェックを追加する」で済ませず、その場で`getCurrentUser`＋ロールチェックを実装する（インフラ未整備等の理由がある場合のみ、チーム判断でTODOを許容する）
- [ ] リソース固有の権限（例：`system_admin`専用、特定organizationのみ）は`requireXxx()`のようなヘルパーに切り出し、複数ルートから再利用する
- [ ] 権限不足は403、未ログインは401、リソース不存在は404と、意味に応じたステータスコードを返す（403になるべき箇所が500や404にならないか確認する）

## 4. アーキテクチャ / ディレクトリ規約（`app/CLAUDE.md`準拠）

- [ ] `repository.ts`にビジネスロジック（デフォルト値の決定、ID生成、ロール割り当て等）を書かない。判断はすべて`service.ts`側で行い、`repository.ts`には完成済みのデータを渡す
- [ ] 新規ファイルを置く場所は、既存コードの慣習（間違っている可能性がある）ではなく`app/CLAUDE.md`のディレクトリ構成を正として決める。特にPrisma Client・Firebase Admin SDKラッパー等バックエンド専用の共通処理は`src/lib/api/`配下に置く
- [ ] Prisma Clientなど共有シングルトンのimportパスは、プロジェクト全体で1箇所に統一する（ファイルごとに違うパスからimportしない）

## 5. Prismaスキーマ変更

- [ ] `schema.prisma`を変更したら、**同じ作業の中で**マイグレーションファイルを作成する（後回しにしない）
- [ ] ローカルにDB接続がない場合でも、`npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script`でSQLを生成し、`prisma/migrations/<timestamp>_xxx/migration.sql`として手動配置できる（`migrate dev`はDB接続が必要なため使えないことがある）

## 6. 型安全性

- [ ] Prismaが生成する型（enum等）とアプリ独自の型が同じ値を表す場合、`as`キャストで無理やり合わせない。直接代入して、将来型が乖離した際にコンパイルエラーで気づけるようにする
- [ ] enum的な値の一覧（例：ステータスの取りうる値）を、TSの型定義とzodスキーマの両方に別々にリテラルで書かない。片方（例：`types/`側の`as const`配列）を正とし、もう片方はそこから`z.enum(...)`等で導出する。ただし`schema.prisma`のenumはDSLが別なので、DBスキーマとTS側の同期は手動確認が必要な境界として残ることを認識しておく

## 7. データ整合性

- [ ] メールアドレス等、人間にとって「実質同じ値」が複数の表記で存在しうるフィールド（大文字小文字、前後空白）をDBの一意制約でチェックする場合、保存前に正規化する（例：`.trim().toLowerCase()`）。正規化しないと、DBの一意制約をすり抜けて重複登録が起きる

---

## 使い方

- **実装時**：このAPIリソース（route/service/repository一式）を書き終えたら、上のチェックリストを上から順に自己チェックしてから完了報告する
- **レビュー時（`/code-review`）**：指摘を出す前に、このチェックリストでカバーされている観点を優先的に確認する。新しいパターンの指摘が出た場合は、このファイルに項目を追記して次回以降のレビュー・実装に活かす
